# Допущения и проверенные факты

Формат: **ID — утверждение** · статус (✅ проверено / ⚠️ допущение / ❓ неизвестно) · на чём основано. В коде допущения помечаются `// ASSUMPTION: A<n>`.

## A1 — Загрузка данных из браузера без сервера · ✅ проверено 2026-10-09

**Как проверял.** Страница `docs/cors-probe.html` запускалась с dev-сервера Vite (`http://localhost:5179`) в Chromium (Playwright). Чтобы повторить: скопировать файл в `public/`, запустить `npm run dev` и открыть `/cors-probe.html`.

| Вариант | URL | Результат из браузера |
|---|---|---|
| gviz CSV | `/gviz/tq?tqx=out:csv&sheet=QUESTS` | ✅ 200, `response.type = "cors"`, `text/csv` |
| **export CSV** | `/export?format=csv&gid=<gid>` | ✅ 200, `cors`. Редирект на `*.googleusercontent.com`, fetch проходит его прозрачно; BLUEPRINTS ≈ 1,1 МБ |
| gviz JSONP | `/gviz/tq?sheet=…&tqx=out:json;responseHandler:cb` | ✅ работает (183 строки) |
| pub CSV | `/pub?output=csv&gid=…` | ⚠️ отвечает 200 `cors`, содержимое не проверялось. Таблица, похоже, не «опубликована в интернете», так что на этот вариант не опираемся |

**Выбор: основной — `export?format=csv&gid=…`, запасной — gviz CSV по имени листа.**
Почему не gviz по умолчанию: gviz сам определяет тип каждой колонки и **выбрасывает значения «неосновного» типа**, а ещё склеивает строки-заголовки. Сравнение тех же листов (`npm run dump-sheets -- --gviz`):

| Лист | Непустых ячеек export → gviz | Что потеряно в gviz |
|---|---|---|
| BLUEPRINTS | 141 508 → 135 717 | ~5 800 ячеек |
| QUESTS | 2 611 → 2 532 | заголовки `Monster Health`, `Barrier …` и др. (198 → 183 строки) |
| QUEST LEVELS | 742 → 728 | **названия всех локаций** |
| CHAMPIONS | 789 → 602 | имена чемпионов, `Element`, Element Breakpoints |
| HEROES | 2 820 → 2 817 | заголовки групп |

Для «карточных» листов это фатально, поэтому gviz — только запасной вариант. Он нужен, если у листа поменяется gid: имя листа стабильнее. Минус export — нужен gid, сейчас они захардкожены в `src/data/fetchSheet.ts` (`SHEET_GIDS`). Если export вернёт HTML, `fetchSheet` выдаст понятную ошибку, и вызывающий код сможет переключиться на gviz.

## A4 — Единицы процентов · ✅

BLUEPRINTS: EVA/CRIT хранятся дробью (`0.05` = 5%). HEROES/CHAMPIONS: строки `30%`, `20% (+20%)`, где в скобках указан вклад врождённого навыка, уже учтённый (примечание на листе: «Hero stats listed take into account the hero's innate skill»). Нормализуем к дроби.

## A5 — Духи: складывание, навык «+», бонус сродства · ✅ / ⚠️

- ✅ **Навыки одинаковых духов складываются** (3 × Walrus = +15% HP). Сверка с fixtures/heroes.txt: без складывания RMS ошибки ATK 9,1% / DEF 5,9% / HP 13,5%, со складыванием — 2,8% / 2,1% / 8,0%.
- ✅ Описания духов в экспорте TitansDB совпадают с обычной (не «+») версией навыка.
- ✅ **Дух вставляется в ЛЮБОЙ предмет: сродство — бонус, а не разрешение** (сессия 26). Официальные заметки 9.0.0 (Blueprint Spirit Affinities): «It works the same as the Elemental Affinity explained above, but replaces the element score bonus with a slightly stronger Spirit skill effect» — [version-9-0-0-release-notes](https://playshoptitans.com/news/version-9-0-0-release-notes/) (цитата проверена по копии вики: https://shop-titans.fandom.com/wiki/Version_9.0.0_Release_Notes). То есть «+»-версия и есть это «slightly stronger effect»: правило `SPIRIT_PLUS_RULE = 'affinity'` подтверждено источником.
- ⚠️ «+»-версия — когда `Spirit Affinity` предмета = навык духа (`SPIRIT_PLUS_RULE`), статы духа ×`SPIRIT_AFFINITY_MULTIPLIER` = 1.5. **Не проверено:** в фикстуре нет ни одного духа в предмете своего сродства. Величина ×1,5 — допущение: в вики «+»-версии отличаются от обычных по-разному (Titan Spirit +15% → +20% HP, Behemoth +13/+5% → +18/+8%), это отдельные строки SKILLS, а не один множитель.
- Связь «дух → навык» точная (ключ игры с playshoptitans.com), совпадает для всех 40 духов.
- В редакторе героя (`heroEditor.ts → slotEnchantChoices`) список духов поэтому полный для любого предмета, а совпадение со `Spirit Affinity` помечается «✦ сродство» (A65).

## A6 — Сродство стихии (Elemental Affinity) · ⚠️ различимо слабо

**✅ Границы правила подтверждены источником (сессия 26).** Официальные заметки 9.0.0 ([version-9-0-0-release-notes](https://playshoptitans.com/news/version-9-0-0-release-notes/), Blueprint Elemental Affinities): «Elements that don't match the blueprint's affinity can still be enchanted like before. They simply won't receive the special benefits» — камень любой стихии вставляется в любой предмет, сродство включает только бонус. Прежняя модель редактора («камень допустим, только если стихия есть в `Elemental Affinity`») была неверной (исправлено, A65).

Камень стихии в предмете с подходящим сродством (`All` = любая) усиливается ×1.5 (`ELEMENT_AFFINITY_MULTIPLIER`); что именно усиливается — `AFFINITY_SCOPE`. Сверка (RMS ATK / DEF / HP при подобранной модели базы):

| Вариант | ATK | DEF | HP |
|---|---|---|---|
| без бонуса (×1) | 3,6% | 2,5% | 6,9% |
| ×1.5 только камень | 2,8% | 2,1% | 8,0% |
| **×1.5 камень и дух (выбрано)** | **2,2%** | **2,1%** | 9,4% |
| ×2 только камень | 2,2% | 2,3% | 9,4% |
| ×1.5 весь предмет | 5,1% | 5,4% | 10,9% |

ATK однозначно лучше с бонусом; пара Geomancer 26 (одинаковая база, у обоих Owl Wing Wand с камнем Water) сходится при «камень + дух ×1.5…1.7». HP предпочитает отсутствие бонуса, но HP-сверка зашумлена моделью базы (A8). **Величину стихии сродство не меняет** (у Нины, Ирвина, Денама, Рейнелла камни в предметах своего сродства, а стихия в экспорте = сумма камней).

## A7 — Множители качества · ✅ частично

Normal ×1, Superior ×1.25, Flawless ×1.5, Epic ×2, Legendary ×3 к ATK/DEF/HP.
- ✅ Legendary ×3 и Flawless ×1.5 — пример Combat Compendium (Wand of Midas 410 → 1230, Tarot Deck 530 → 795).
- ✅ Superior ×1.25 — пара Geomancer 26: у Вестии Superior броня, у Логарсона Normal, вычисленная база DEF 276,4 и 277 (при ×1.2 разошлась бы на 12).
- ⚠️ Epic ×2 в фикстуре есть (4 героя), отдельно не выделялся; ошибки у этих героев в пределах общей.
- ✅ **Статы камней и духов качеством не масштабируются** (компендиум: Tide даёт 38 ATK и Legendary-жезлу, и Flawless-колоде).
- Округление после множителя — `Math.round` (не проверено: разница ±0,5 тонет в шуме модели базы). Пример Mistpeak Bloom из статьи не годится — значения предмета с 2020 года изменились.

## A8 — База героя по уровню · ⚠️ модель + сверка с таблицей stcalc

Статов по уровням нет ни в HEROES (одно значение на класс), ни в HERO LEVELS (XP и макс. тир) — перепроверено в сессии 3. Сторонних источников нет: на playshoptitans.com страниц героев нет, трекер shoptitans.dowob.dev требует входа. По словам игроков, прирост — своя таблица на класс и уровень, нелинейная (Reddit: «Dancer 1–12 ур. +1–3 HP за уровень, с 12-го +5–8»). В сессии 31 нашлась таблица stcalc.com — она подтверждает, что рост ступенчатый, но в код её встраивать нельзя (лицензии нет), поэтому коэффициенты по-прежнему подбираются по своим экспортам, а таблица служит проверкой.

### Модель и переподбор (сессия 31)

**Обратный счёт:** для каждого героя база = итог / (1 + Σ%) − Σ вкладов предметов − плоские прибавки. Форма:

```
база(L) = база₁ · (1 + k·x + d·x²) + c·x,   x = L − 1
```

`база₁` — статы класса из HEROES, `k` и `c` — свои на группу класса (Fighter/Rogue/Spellcaster), `d` — один на стат. Коэффициенты — МНК по относительной ошибке итогового стата **сразу по двум фикстурам** (18 героев 23–33 ур. + 19 героев 31–37 ур.); форма выбрана по ошибке leave-one-out (LOO: каждый герой предсказан моделью, подогнанной без него), проверка — по таблице stcalc (42 класса × 50 уровней):

| Форма на стат | параметров | LOO ATK | LOO DEF | LOO HP | таблица: ATK / DEF / HP |
|---|---|---|---|---|---|
| база₁·(1 + k·x) + c·x (было) | 2 | 3,0% | 2,7% | 10,7% | 67 / 85 / 32% |
| та же + d·x² | 3 | 2,3% | 2,3% | 10,6% | 56 / 76 / 23% |
| та же + d·база₁·x² | 3 | 2,2% | 2,2% | 10,5% | 60 / 71 / 21% |
| k, c по группам классов | 6 | 3,1% | 2,8% | 8,6% | 66 / 78 / 35% |
| k, c по группам + d·x² | 7 | 2,1% | 2,2% | 7,7% | 52 / 64 / 26% |
| **k, c по группам + d·база₁·x² (выбрано)** | 7 | **1,9%** | **2,1%** | **7,7%** | **58 / 61 / 24%** |

Итог (`HERO_LEVEL_STAT_GROWTH`; порядок групп Fighter / Rogue / Spellcaster): ATK k −0,0835 / −0,2336 / −0,1087, c 6,614 / 9,724 / 9,317, d 0,013; DEF k −0,0664 / −0,2716 / 0,022, c 7,419 / 9,181 / 4,577, d 0,0113; HP k 0,0748 / −0,143 / −0,0654, c 0,171 / 5,021 / 3,259, d 0,0041.

**RMS модели без эталона, до → после (переподбор по обеим фикстурам):**

| Набор | ATK | DEF | HP |
|---|---|---|---|
| fixtures/heroes.txt (18 героев, 23–33) | 2,1 → 1,4% | 2,1 → 1,7% | 9,0 → **5,6%** |
| fixtures/heroes-2026-10-12.txt (19 героев, 31–37) | 3,8 → 1,7% | 3,3 → 1,6% | 11,4 → **7,3%** |
| обе вместе (37) | 3,1 → 1,6% | 2,8 → 1,6% | 10,3 → **6,5%** |

Часть улучшения ATK на новой фикстуре дала не база, а пересмотренная A29 (стихия от сродства предмета): 5,1 → 3,8% ещё до переподбора. Цель «HP ±3%» по-прежнему не достигнута — см. «Что осталось».

### Что показывает таблица (и почему расхождение с ней большое)

По поднабору «базовые 21 класс» расхождение модели с таблицей: ATK RMS 54,7 → 48,5%, DEF 58,6 → 47,0%, HP 23,4 → 15,3% (по всем 42 классам 58 / 61 / 24%). Причина не столько в форме роста, сколько в **компенсации**: эталонная база героя (та, что воспроизводит экспорт точно) выше табличной на ATK +34,6% (старая фикстура) и +45,7% (новая), DEF +36…37%, HP +13…21%. То есть модель предметов недобирает ATK/DEF, и база это скрывает — иначе итоговые статы героев разошлись бы с экспортом. У HP наоборот: модель роста близка к таблице (15,3% по базовым классам), поэтому остаточные 5,6 / 7,3% — это в основном настоящая ошибка роста, а не предметов.
Границы в тесте (ATK/DEF ≤ 70%, HP ≤ 30%) — регрессионный сторож, а не цель.

## A9 — Семантика барьера · ⚠️ допущение

`Barrier Type` — список стихий, `Barrier Health` — число. Допущение: барьер пробивается, если суммарная величина стихии отряда в **любой** из перечисленных стихий ≥ `Barrier Health`. Не пробит — урон отряда сильно снижается. Точная механика (порог или пропорция, вклад чемпиона, «Any») в таблице не описана. Есть косвенные подсказки в SKILLS: `+50% party Element bonus VS Elemental Barriers`, `Can use any element, but only counts as N% against Elemental Barriers`.

**✅ Величина подтверждена (сессия 22):** ST-Central, «Hero Academia» → Elemental Barriers (https://st-central.net/hero-academia/, изменено 25.05.2026): «If the barrier's health is higher than the elemental value of your party then it will be active, **causing you to do 80% less damage during the entire quest**» → ×0.2; там же — Spellblade бьёт барьер на 50%, чемпионы засчитываются своей стихией.

**Сессия 5 (симулятор):** не пробит → урон отряда ×0.2 (`BARRIER_UNBROKEN_DMG_FACTOR`); стихия бойца для барьера — отображаемая (камни + бонус сродства, A29), чемпион — по Element Breakpoints ранга; «Any» (Spellblade) — 50% от суммы камней против любой стихии барьера; `+N% party Element bonus` (Rudo) — множитель к сумме отряда. Реализация: `combat.ts → barrierBroken`.

**✅ Подтверждено гайдом (сессия 16).** «Гайд по героям и защитникам Shop Titans 2.0» (Develion, https://docs.google.com/document/d/1DrP0VBxnDPSLwsLe_Y8T3BkrGmN_f6QiBGrHW1qs3E8), раздел «Экстрим-приключения», п. 1:
«Боссы Экстрим-Приключений имеют стихийный барьер, **уменьшающий получаемый боссом урон на 80%**» — это ровно `BARRIER_UNBROKEN_DMG_FACTOR = 0.2` (непробитый барьер: урон отряда −80%). Там же подтверждены обе частные механики: Rudo `+N% party Element bonus VS Elemental Barriers` (в примере гайда стихия отряда 200 → 300 против барьера) и Spellblade `Can use any element, but only counts as 50% against Elemental Barriers` — так они и смоделированы (`statWeights.ts → partyElementBonusPct`, `combat.ts → barrierBroken` через `barrierAnyPct`/`elementAny`). Как читался гайд — в PROGRESS, сессия 16.

## A10 — Пороги защиты квестов — внешний источник · ⚠️

В таблице их нет. Источник — https://stcentral-hub.github.io/posts/main-quests/: статичный HTML, `Access-Control-Allow-Origin: *`, значит, из браузера читается без прокси. Формат: на сложность `50% X · 70% 2X · 75% 6X` (DEF → снижение урона). Lost City of Gold там нет.
Лицензия **CC BY-NC-ND 4.0**. **Решение владельца (сессия 2):** в snapshot.json и в репозиторий не кладём. `src/data/breakpoints.ts` загружает страницу в рантайме из браузера (CORS `*` проверен в Chromium), разбирает её регулярками (без DOM — работает в воркере и в тестах) и кэширует в IndexedDB на 7 дней. В UI («Данные») показан источник со ссылкой и лицензией. Если страница недоступна и кэша нет — режим «без порогов» (`mode: 'noCaps'`) с предупреждением. Поэтому `scripts/build-breakpoints.ts` не делался. В тестах — самодельный HTML той же разметки с выдуманными числами.
Сопоставление: блок локации и следующий за ним блок босса, сложность — по `title`. Покрыто 112 из 138 квестов (все, кроме Lost City of Gold). HP монстров на сайте совпадает с таблицей во всех 112.

## A21 — Стихия героя · ✅ / ⚠️

✅ Стихия героя = сумма камней **его** стихии плюс бонус сродства предмета к камню (A29, пересмотрено в сессии 31: совпадает с экспортом у всех героев обеих фикстур, кроме Селены — у неё ровно +5, не объяснено). ## A29 — Стихию даёт сродство предмета, а не дух · ✅ пересмотрено в сессии 31

До сессии 31 считалось, что +5 стихии дают духи Ox и Chimera (`SPIRIT_ELEMENT_BONUS`): в старой фикстуре Селена (1× Ox Spirit) показывала 95 при 90 по камням, а Джорди (6× Chimera Spirit) — 180 при 150. Вторая фикстура (`fixtures/heroes-2026-10-12.txt`, 19 героев 31–37 ур.) это опровергла: у Селены там **нет Ox Spirit**, а излишек +5 остался; у Джорди 6× Leviathan дали +30. Духи стихии не дают вовсе — совпадал другой признак: **Elemental Affinity предмета**.

Правило (сверено по обеим фикстурам): камень в предмете, чьё `Elemental Affinity` включает его стихию («All» — любую), даёт **+10 стихии**, если величина камня ≥ 25 (T12 и выше).
- T14 (35) и T12 (25): Логарсон 5 слотов → +50 (экспорт 260 против 210 по камням), Вестия 4 → +40, Джорди 3 → +30, Ирвин 1 → +10, Хуан 1 → +10, Беовульф 1 → +10; в старой фикстуре Джорди 3× T12 → +30.

- **Не объяснено:** Селена в обеих фикстурах имеет ровно +5 сверх камней — её CM-73 Jetboots со сродством «All» и камнем T9. Под это правило не подгонялось; в тесте зафиксировано как единственное исключение из сверки стихии.

- Стихия для барьера и стихия для порогов ступеней навыков (A12) теперь считаются одинаково: `heroElementValue` возвращает `element` и `elementStones` (совпадают), различие осталось только в API. Реализация: `constants.ts → AFFINITY_ELEMENT_BONUS`, `AFFINITY_ELEMENT_MIN_STONE_VALUE`, `stats.ts → heroElementValue`.


## A30 — Формулы боя · ✅ Combat Compendium (сессия 5)

Источник: https://st-central.net/combat-compendium/ (CC BY-NC-ND 4.0, только формулы, без копирования текста).
- Враг бьёт первым. Порядок ходов отряда: 3 слота — средний→левый→правый; 4 — средний-левый→крайний левый→крайний правый→средний-правый (для 5 — не опубликован, у нас от центра влево, A33).

## A34 — Штраф уклонения на Extreme: −20 п.п. из суммы, до предела · ✅ подтверждено гайдом (сессия 16)

«Гайд по героям и защитникам Shop Titans 2.0» (Develion, ссылка в A9), раздел «Экстрим-приключения», п. 2:
«Уворот ваших героев уменьшается на 20%… Однако **штраф в 20% вычитается из общего значения уворота** и чтобы полностью нивелировать его, следует разогнать уворот до 95%».

Значит, штраф — **вычитание** 20 п.п. из суммарного EVA, и только потом применяется предел (A42): 95% − 20 п.п. = 75% — ровно предел. При умножении (×0.8) для выхода на 75% хватило бы 93,75%, что противоречит «95%» из гайда. **Прежняя гипотеза (×0.8) отброшена** — она выводилась из формулировки r/shoptitans «the 20% penalty Extreme and Terror Difficulty have».

Порядок в движке: `eva = сумма статов − 0.20 (если Extreme)`, затем `min(eva, предел героя)`; при сумме ниже 20 п.п. уклонение становится отрицательным — это включает A59 (повышенный шанс крита врага).
Реализация: `constants.ts → EXTREME_EVA_PENALTY`, `combat.ts → effectiveEvasion` (вызов в `tryHit` и в `score.ts → quickScore`). Тесты: `combat.test.ts` — 95% на Extreme даёт ровно тот же бой, что 75% на обычной сложности.

## A37 — Ролевая эвристика оптимизатора · ⚠️

«Танк» в отряде — герой с наибольшим DEF базового набора; он оптимизируется первым. При близких quickScore (±1%) танку предпочитается DEF (не выше порога 75% квеста — дальше снижение урона не растёт) и угрозу, ДД — ATK и HP. Порядок: сначала каждый герой по ролям (остальные — в текущей экипировке), затем совместная доводка по всем слотам. Точная игровая формулировка ролей неизвестна — эвристика влияет только на порядок и тай-брейки, финальный выбор делает симуляция. Реализация: `optimizer.ts → betterQuick`.

## A38 — Отсев: «разнообразные» кандидаты, адаптивный K и локальный поиск · ⚠️ (сессия 7)

Чистый top-K по quickScore терял лучший по симуляции вариант слота в 21,7 % случаев (см. PROGRESS.md, сессия 6). Разбор промахов показал: чаще всего отсекались предметы со **вторичным статом** (12/26) и с **связью стихии** (7/26) — quickScore недооценивает их вклад. Три приёма, не раздувающих бюджет симуляций:
1. **Разнообразные кандидаты** — кроме top-K в отсев всегда попадают лучший по каждому измерению (ATK, DEF, HP, EVA, CRIT, величина стихии), лучший артефакт и лучший со связью стихии (`selectSlotCandidates`).
2. **Адаптивный K** — если quickScore K-го и (K+5)-го кандидатов различаются не более чем на `OPTIMIZER_K_ADAPT_TOL = 0,05` от значения (полка оценок плоская, ранг ненадёжен), K расширяется на 5 и проверка повторяется. Порог подобран на 120 случаях (`optimizer.prune.test.ts`), игровых данных нет.
3. **Локальный поиск** — после координатного спуска для каждого слота симуляцией проверяются `OPTIMIZER_LOCAL_NEIGHBORS = 3` следующих по рангу quickScore кандидата (число — эвристика).
После правки промах отсева — 2,5 % (3/120), потеря win rate при промахе 0 п.п. (все оставшиеся промахи — «ничьи»: win rate совпадает с лучшими из множества). Реализация: `optimizer.ts → selectSlotCandidates`, `pruneSlot`, локальный поиск в `runOptimizer`.

## A39 — Лексикографический тай-брейк и кубики для перекидки навыков · ✅ / ⚠️ (сессия 12)

Две части:
1. **Тай-брейк финального выбора.** В исходном наборе из 120 случаев 74 % вариантов имеют win rate ровно 0 % или 100 % (замер — `optimizer.prune.test.ts`), цель на них не различает наборы. Финальный выбор упорядочен лексикографически: win rate → средние раунды (меньше) → средний минимальный % HP среди выживших (больше, `SimMetrics.avgMinSurvivorHpPct`) → урон/раунд (больше). На откалиброванном наборе из 30 случаев с базовым win rate 20–80 % промах отсева — 0/30. Если у нескольких проверенных наборов цель совпадает, `OptimizerResult.tieBreakUsed = true`, и UI показывает, что выбор сделан по тай-брейку.
2. **Кубики — подтверждено ST-Central** («Skill Rerolls: A Basic Breakdown», https://st-central.net/skill-rerolls-roland/, изменено 22.11.2025; слоты независимо подтверждены японской вики по Tower of Titans). Дословно про слоты:
   - Basic — «Used to reroll skill slot 1 or fused into super skill die»;
   - Super — «Used to reroll skill slot 1 & 2 or fused into mega skill die»;
   - Mega — «Used to reroll skill slot 1, 2, & 3 or fused into perfect skill die»;
   - Perfect — «Used to reroll skill slot 1, 2, 3 & 4».

   **Как это читать — исправлено в сессии 17.** Перечень — это слоты, **к любому из которых** кубик применим: роллится один выбранный слот, младшие не трогаются. Прежнее чтение («кубик k перекидывает и все младшие слоты», из него родилось предупреждение «следи, чтобы там не было нужных навыков») **отброшено**.
   - **Противоречие.** Формулировка ST-Central допускает оба чтения: «slot 1, 2, & 3» можно понять и как «перекидывает все три сразу». Прямого «only the chosen slot» в статье нет.
   - **Решение — по гайду Develion** (ссылка в A9), раздел «Как “роллить” героев»: героя нанимают, пока нужный навык не встанет **во 2-й** слот, затем качают до 35 и роллят **4-й** слот идеальным кубиком, а 1-й — базовым. Если бы идеальный кубик перекидывал младшие слоты, он стирал бы только что выбранный 2-й навык и весь найм терял бы смысл — гайд такого не предполагает.
   - **Второй довод — та же статья ST-Central**, раздел «Perfect but lazy»: S4 роллят кубиками из Башни Титана, S1 — базовым кубиком **после** этого, а S3 закрывают Роландом («S3 — Wait until S1/S2/S4 are done before using Roland's ability»); при чтении «перекидывает все младшие» порядок «сначала S4, потом S1» невозможен.
   - **Следствие для кода:** `CUBE_SLOTS[k]` — список слотов, к которым кубик применим; `cubeForSlot(slot)` возвращает самый дешёвый подходящий (слот 1 → базовый, 2 → супер, 3 → мега, 4 → идеальный); предупреждение о младших слотах и логика вокруг него удалены. Тесты — `skills.test.ts` («идеальный кубик в 4-м слоте не трогает 2-й»).
   - **стоимость:** «A single T2 costs double that of a T1, T3 is 4x a T1, and T4s are 8x» → супер = 2 базовых, мега = 4, идеальный = 8 (плюс flawless-предмет соответствующего тира — в совете не учитываем);
   - **Роланд:** любой навык в любой слот, но «ONCE per hero» → советуем тратить последним, обычно на слот 3 (в статье: «slot 3 is usually the hardest slot to roll using dice»), и держать до конца;
   - **«проверка одним кубиком» (ODC):** «throwing one single T1 die at them to reroll their first slot once» для сомнительного героя; если и он пустой — героя менять, не тратиться дальше.
   ⚠️ Остаётся допущением **соответствие кубик → максимальный тир навыка** (`CUBE_MAX_TIER` 10/15/20/25): в ST-Central про тиры ничего нет, в данных таблицы тоже. Совет по тиру показывается отдельной оговоркой.
3. **Блокировки (A40)** учитываются в `reasons`.

## A41 — Ограничения подбора по умолчанию и оценка «+1 тир / +1 качество» · ⚠️ (сессия 11, уточнено в 13 и 26)

Инвентаря больше нет: всё покупается на рынке, пул — любые предметы таблицы. «По карману» задают ограничения по умолчанию (требование владельца, `src/engine/constraints.ts → defaultConstraints`): **макс. тир = макс. тир надетого у ЭТОГО героя + 1** (`OptimizerConstraints.perHero`, `optimizer.ts → capForHero`; уточнение сессии 13 — раньше бралось по всему отряду, и слабому герою предлагались вещи под сильного), **но не выше `Max Item Tier` его уровня** (HERO LEVELS; сессия 26 — та же `maxItemTierFor`, что в редакторе, см. A66); то же для камней; без надетых — потолок уровня; качество ≤ Superior; духи — все, кроме Titan Spirit, если хоть у одного героя отряда нет «Души Титана» (с учётом переключателя «Душа Титана» на странице). Переопределения пользователя (`maxItemTier`/`maxStoneTier`) остаются **общим потолком**: итог для героя = min(его собственный потолок, потолок отряда, потолок уровня); ручной список духов снимает per-hero ограничения.

⚠️ **Ограничение «Titan Spirit — только при Душе Титана» — допущение без источника** (сессия 26). Ни в данных (в ENCHANTMENTS/BLUEPRINTS нет полей требований), ни в официальных заметках, ни в гайде Develion такого правила нет; в редакторе героя оно поэтому **снято** (A65). В подборе по умолчанию Titan Spirit оставлен исключённым как самое дорогое зачарование (T14, `Supreme Runestone`, 4 000 000 стоимости) — это ограничение «по карману», а не правило игры; кнопка «все» в списке духов его включает.

Оценка апгрейда (`upgradeScenarios` / `upgradeOutcome`): подбор повторяется с ограничением на ступень выше (тир +1 или следующее качество), стартуя с уже найденного набора, на урезанном бюджете `OPTIMIZER_WHATIF_SIM_BUDGET = 150` симуляций и с тем же seed (CRN). Потолки героев поднимаются вместе с общим, но не выше `Max Item Tier` уровня (A66): если уровень не даёт ступени выше, сценарий «+1 тир» не предлагается вовсе. Если сценарий не нашёл лучше — прирост считается 0 (текущий набор остаётся доступен), т. е. оценка — нижняя граница. Прирост < `WHATIF_WORTH_MIN_DELTA = 1 п.п.` UI называет «в пределах шума» — порог по шуму симуляции, игровых данных нет.

## A42 — Предел уклонения 75% (78% у Pathfinder) · ✅ подтверждено гайдом (сессия 16)

## A54 — Ninja/Sensei: врождённый бонус EVA/CRIT · ✅ исправлено (сессия 15), ⚠️ величина у промоушена

В HEROES базовые EVA/CRIT класса уже включают врождённый навык (`Ninja: Crit 20% (+20%)`, `EVA 30% (+20%)` — A4/A26): сверка с экспортом (Ирвин 71/20, Нина 56/30) сходится именно при таком чтении. Поэтому **в бою бонус не добавляется второй раз, а снимается после первого полученного урона** («until damaged»); у Sensei `Regain bonuses after 2 rounds` возвращает его через 2 раунда без урона (A49).

- **Величина — из HEROES, а не из текста ступеней.** Скобки дают +20% EVA / +20% CRIT, тогда как текст ступеней обещает другое (+15% EVA у T1/T2, +20% у T3 Ninja, +40% CRIT у T3, +25%/+50% у ступени за Душу Титана). Решение владельца (сессия 15): при противоречии берём HEROES — именно эта величина уже сидит в базовых статах, её и надо снимать.
- **Промоушен.** У карточки Sensei скобки не заполнены (`EVA 30%`, `Crit 20%` — те же числа, что у Ninja), поэтому величина берётся у базового класса (`stats.ts → innateBonusOf`). Иначе у Sensei механика «until damaged» + «Regain bonuses» не меняла бы ничего: бонус не добавлялся бы и не снимался.
- **Реализация:** `stats.ts → activeInnateSkill` (какой навык бойца врождённый), `innateBonusOf`; `combat.ts → Fighter.innateSkillId/innateBonus`, `isInnateBakedIn` (эффект не идёт в боевые модификаторы), `innateBonusLoss` (после урона вычитает величину из HEROES), вызов в `computeMods`.
- **Проверка:** `classMechanics.test.ts` — «Ниндзя без урона имеет статы из экспорта: бонус не добавлен второй раз» (модификаторы боя равны версии без врождённых навыков вовсе), «после удара статы меньше ровно на величину бонуса» и интеграционно (с потерей бонуса герой гибнет раньше и наносит меньше урона), плюс возврат бонуса у Sensei через 2 раунда; `stats.fixture.test.ts` — сверка статов не изменилась (EVA/CRIT у всех 18 героев как и были, `calcStats` не трогали). В отчёте `modelingReport` Ninja и Sensei теперь «полностью» (с пометкой про величину), «частично» остаётся только Bjorn (A53).
- **Что осталось непроверенным:** экран игры для Sensei (в HEROES у промоушена скобок нет) и то, что игра снимает бонус ровно на величину из скобок, а не по тексту ступени.

## A56 — Веса статов и «зонд» для насыщенных квестов · ⚠️ (сессия 13)

Веса статов (`src/engine/statWeights.ts`) — измерение, а не формула: для каждого героя считается симуляция с прибавкой `+1% CRIT`, `+10% CRIT DMG`, `+1% EVA`, `+5% ATK/HP/DEF`, `+10 стихии`, `+10 угрозы` на **общем seed** с базовым прогоном (CRN), поэтому разница не шум. Метрика: win rate не насыщен → прирост win rate (п.п.); 100% → урон за раунд, а для HP/DEF/EVA — мин. % HP выжившего (добавка защиты урон за раунд не увеличивает). Шаги заданы требованием владельца; допущениями остаются метрика на насыщенных квестах и поведение зонда:

- **win rate 0%** (отряд проигрывает всегда): на самом квесте ценность статов не измерима — дельты лежат в пределах шума единичных прогонов. Веса считаются на **ослабленном зонде**: `weightsProbeQuest(quest, factor)` делит HP монстра на `factor`, а урон — на `√factor` (мягче, иначе квест превращается в лёгкую прогулку и статы перестают быть нужны); перебор `WEIGHTS_PROBE_FACTORS = [4, 8, 16, 32, 64, 128, 256]` на укороченных прогонах, победитель — зонд с win rate ближе к 50 % (`PROBE_WIN_RATE_MIN/MAX = 0.1/0.9`, `PROBE_TARGET_WIN_RATE = 0.5`), затем он пересчитывается на полном числе прогонов. UI помечает такие веса и показывает факторы. Сами величины — эвристика (игровых данных о «зондах» нет), поэтому абсолютные значения весов на непроходимых квестах оценочные.
- **win rate 100%**: веса по урону шумные (бой кончается за 2–8 раундов), поэтому у защитных статов берётся мин. % HP выжившего, а дельты win rate в этом режиме не показываются как метрика.
- Доли атак босса (`combat.ts → threatShares`) — аналитическое ожидание (20% AoE по всем живым, остальное по `threat / Σ threat`), а не замер по прогонам; вклад в барьер (`elementContributions`) — модель A9 (камни + духи Ox/Chimera, «Any»-классы и бонус Rudo).

| `CombatModel.negativeEvaCrit` | `combat.ts → enemyCritChanceVs` | как надбавка за отрицательный EVA складывается с базовым критом врага: `additive` (10% + 5%) или `absolute` (надбавка задаёт шанс: 5%) | A59 |
| `CombatModel.pctStacking` | `formulas.ts → combatStat` | как % боя (ауры, условные навыки) складываются с % карточки: `pooled` (Compendium) или `multiplicative` | A62 |

Какие из них реально влияют на ошибку — измеряется, а не угадывается: `src/engine/calibration.ts → MODEL_VARIANTS` (20 вариантов) и `TUNING_KNOBS` (7 числовых крутилок с диапазонами; режимы вида `negativeEvaCrit` проверяются вариантом, а не крутилкой — крутилка умеет только числа). Результаты — `npm run calibrate` → `docs/CALIBRATION.md`, до/после — `docs/PROGRESS.md`.

**Ограничение метода.** Подгонка по отметкам подстраивает модель под выборку пользователя (десятки боёв, не случайная выборка локаций), поэтому выигрыш по Brier на ней — не гарантия точности на новых боях; от переобучения защищают два правила: (1) крутим не больше 2–3 самых влиятельных параметров, (2) сверка статов по `fixtures/heroes.txt` не должна ухудшиться больше чем на `FIXTURE_RMS_GUARD = 0.5 п.п.` (`tsc`/тесты не дадут молча уехать). Подгонка **записывается в отчёт**, а не правит константы автоматически: смена значения в `constants.ts` — отдельное решение с обновлением этого файла.

## A58 — Метрика «точность модели»: порог 50 % и Brier по бинарной отметке · ⚠️ (сессия 14)

Отметка пользователя бинарна («прошёл / не прошёл»), поэтому «доля верных» считается при пороге win rate 50 % (`«проходит» ↔ win rate ≥ 50 %`), а Brier score — `mean((win rate − исход)²)`, где исход 1/0 (`src/engine/calibration.ts → calibrationSummary`). Это **не** вероятность прохождения, которую показала бы игра: сколько бойцов выжило и с каким HP в отметке не сохраняется. Поэтому:

- Brier по отметкам систематически выше, чем был бы по «истинной» вероятности (бинарный исход — шумная метка), сравнивать его имеет смысл только между вариантами модели на одних и тех же отметках;
- вместе с пересчётом показывается Brier по win rate, сохранённому в отметке в момент её постановки (`brierStored`) — это «что модель говорила тогда»; расхождение с пересчётом означает, что модель успела измениться;
- с сессии 24 отметки хранят и погибших героев (`deadHeroes`, A64), и калибровка считает второй Brier — по смерти каждого героя;
- отметки хранят `modelVersion` (`ENGINE_MODEL_VERSION` на момент отметки). Если формулы менялись, отметки старых версий на «Данных» помечаются предупреждением, а калибровка может считать их отдельно: смешивать отметки разных моделей — значит измерять не модель, а историю правок.

## A59 — Крит врага по герою с отрицательным уклонением · ✅ подтверждено гайдом (сессия 16)

Гайд Develion (ссылка в A9), раздел «Экстрим-приключения», п. 2: «Также, если персонаж совсем не имеет уворота, штраф сделает его значение негативным. Герои с негативным шансом уклонения имеют повышенный шанс получить критический удар (**0.25% за каждую единицу негативного уворота**). Таким образом, герои с нулевым уворотом будут иметь 5% шанс на получение критического удара».

Трактовка:
- «единица» негативного уворота — **1 п.п.**, «5% у героя с нулевым уворотом» — **надбавка** к базовым 10% крита врага (A30): 20 п.п. штрафа × 0.25% = 5 п.п. Так на Extreme у героя с нулевым EVA шанс получить крит — **15%** (`0.1 + 0.05`). Иначе «0.25% за единицу» не сходится ни с 5%, ни с 20 п.п.
- Отрицательное уклонение получается **только на Extreme** (штраф A34 уводит сумму ниже нуля). 20 п.п. уворота полностью нивелируют и штраф, и надбавку: и то и другое считается от эффективного EVA после вычитания.
- Шанс считается **на конкретного бойца** (в т. ч. при AoE), а не на отряд: в `runAttempt` крит-ролл идёт внутри `tryHit(i, …)`.

Реализация: `constants.ts → NEGATIVE_EVA_ENEMY_CRIT_PER_PP = 0.0025`, `combat.ts → enemyCritChanceVs` (`tryHit`), `score.ts → quickScore` (множитель входящего урона).
Тесты: `combat.test.ts` — 15% при нулевом EVA на Extreme, возврат к 10% при 20 п.п. уворота, положительное уклонение надбавки не даёт; интеграционно — герой без уворота на Extreme гибнет чаще (на 2000 прогонах разница в выживаемости > 10 п.п.).
Не проверено в игре: величина «единицы» (п.п.) и то, что надбавка именно складывается с базовыми 10%, а не задаёт итог в 5% — взято по указанию владельца (0 EVA → 15%).

**Сессия 17:** неоднозначность вынесена в параметр калибровки `CombatModel.negativeEvaCrit` (A57): `additive` (по умолчанию — 15% при нулевом EVA) и `absolute` (буквальное чтение гайда — 5%). Вариант `negative-eva-absolute` в `MODEL_VARIANTS` измеряет, какое чтение лучше согласуется с отметками «проходит / не проходит»; значение по умолчанию не менялось.

## A60 — План ролла навыков героя · ⚠️ (сессия 17)

Пошаговый план собирает `src/engine/skills.ts → rollPlan` (чистая функция без симуляций: цена плана и число бросков считаются по данным таблицы), показывает его раздел «Навыки: вклад, план ролла и перекидка» на странице «Подбор», а общая памятка — страница «Как роллить» (`src/routes/roll.tsx`).

**Источник шагов** — гайд Develion (ссылка в A9), раздел «Как “роллить” героев»:
1. талант «Лучшие товарищи Аргона» 3-й ступени (**11 очков дерева талантов**) → герои нанимаются сразу **10-го уровня**, где открыт 2-й слот навыка;
2. найм/увольнение, пока нужный навык не встанет **во 2-й слот** — «Именно 2й. Это важно» (бесплатно);
3. прокачка до **35-го уровня** (открывает 3-й и 4-й слоты), «используем Душу Титана если 3й или 4й навыки недоступны»;
4. **4-й слот — идеальный кубик** (8 базовых; добывается в Башне Титана — **8 за башню, 4 без према**);
5. **1-й слот — базовый кубик** (создаётся синтезом);
6. **остаток — Роланд** (любой навык в любой слот, один раз на героя).
Дополнительно: «Если на моменте прокачки героя 3й или 4й навыки попались нужные, просто доралливаете 1й навык кубиком, а оставшийся добираете Роландом»; «Синтезировать кубики выше базового — смерть»; «Сколько кубиков накопить чтобы начать роллить? 20+ идеальных и 100+ базовых».

**Как это отображено в движке:**
- **«нужный навык»** = навык с вкладом выше `SKILL_REROLL_EPS` (совет `keep`). Шагов по слотам с нужными навыками план не предлагает: «2-й слот — оставить».
- ~~Шаг `unblock` («сначала сроллить слабую версию»)~~ — **убран в сессии 23** (A63): пару «слабая ↔ сильная версия» по данным надёжно не связать, а подмена ступени той же линейки в бою ничего не меняет. Измерение вклада «сильной версии» (`stronger`) и `strongerInLine` удалены вместе с шагом.
- **один слот — одно действие** (`HeroSkillPlan.slotActions`): шаг плана («сроллить»: найм, кубик, Роланд) важнее вердикта совета («оставить») — одновременно «оставить» и «сроллить» для одного слота не выводится.
- **цена плана** — в базовых кубиках (`CUBE_BASIC_COST`: 1 / 2 / 4 / 8; найм, прокачка и Роланд — 0). Кубик на слот 2 — супер (2 базовых), потому что базовый умеет только слот 1; если герой ещё не прокачан (уровень ≤ 10), слот 2 закрывается **наймом**, а не кубиком.
- **число бросков**: нужный навык в данных не задан, поэтому у шагов показывается только вероятность конкретного навыка ≈ 1/N (N — пул слота); оценка «в среднем бросков» удалена вместе с шагом `unblock` (сессия 23).
- **пул перекидки** (`rollableSkills`) — ⚠️ допущение: навыки `type = 'Hero'` с ненулевой редкостью, доступные классу героя (и промоушену при Душе Титана), без требующих промоушена у непромоушенного героя, без линеек, уже стоящих на герое, и без второго обычного/эпического навыка на оружие (A40). **Слот-специфичных пулов в данных нет** — пул один на все слоты; в игре вероятности видны в подсказке Reroll Odds, в таблице их нет. Порядок величины совпадает с гайдом: пул 100–150 навыков ⇒ на один конкретный навык уходит ~100+ бросков, отсюда и совет копить 20+ идеальных и 100+ базовых.
- **флажок «Роланд использован»** — состояние интерфейса на героя (`SkillAdviceOptions.rolandUsed` — индексы героев): при нём шаг Роланда не предлагается, цена плана не меняется (Роланд бесплатен). Пересчёт плана при переключении флажка идёт в основном потоке — `rollPlan` не запускает симуляций.
- **константы** (`constants.ts`, источник — гайд): `SKILL_ROLL_HIRE_LEVEL = 10`, `ARGONS_FINEST_TALENT_POINTS = 11`, `SKILL_ROLL_FULL_LEVEL = 35`, `PERFECT_DICE_PER_TOWER = 8`, `PERFECT_DICE_PER_TOWER_NO_PREMIUM = 4`, `SKILL_ROLL_STOCK_IDEAL_DICE = 20`, `SKILL_ROLL_STOCK_BASIC_DICE = 100`. Точные уровни слотов берутся у класса из HEROES (`skillSlotLevels`: у промоушенов, например, 19/29 или 23/35) — 35 остаётся правилом гайда и значением по умолчанию.
- **проверки** (`src/engine/skills.test.ts`): идеальный кубик в 4-м слоте не трогает 2-й слот; нужное во 2-м слоте не тратит ни кубик, ни пере-найм; шага «сроллить слабую версию» нет даже у промоушена с высшей ступенью линейки в пуле, слот 4 — без заявленной цели (1/пул); вклад навыка не зависит от записанной ступени линейки; «оставить» и «сроллить» для одного слота в плане не выводятся (`slotActions`); «Роланд использован» убирает шаг Роланда, не меняя цену; пул не содержит линеек, стоящих на герое. E2E — `e2e/roll.spec.ts` (памятка) и `e2e/optimize.spec.ts` (план и флажок на странице «Подбор»).
- **`ENGINE_MODEL_VERSION` не поднимался:** шаги плана и пул на win rate не влияют, а режим крита по отрицательному EVA (A59) по умолчанию остался прежним (`additive`).

## A62 — % из боя суммируются с % карточки (pooled) · ⚠️ (сессия 22)
Combat Compendium: «ATK = (Base ATK + Seed ATK + (Weapon + Enchants) × (1 + Weapon Skill + Gear Skill) + (Gear + Enchants) × (1 + Gear Skill)) × (1 + ATK Modifiers)» и «**All non-specific ATK modifiers are pooled and applied at the very end**». До сессии 22 бой умножал % аур чемпиона и условных навыков («when HP below», «against bosses», «for N rounds», случайный бонус Tamas) **поверх** стата карточки, где свои % уже применены: (Σ × (1 + P)) × (1 + aura). Теперь — в одну сумму: (Σ + плоские боя) × (1 + P + aura) (`formulas.ts → combatStat`, для ATK, DEF и HP). Косвенно это подтверждает и «Hero Academia» (Sorcerer): «raw attack will outperform weapon damage, up to a point. The general threshold is 350% bonus Attack» — убывающая отдача бывает только у суммируемых %.

Допущение: Compendium показывает суммирование на навыках героя и духа; что **ауры чемпиона** входят в ту же сумму — по аналогии. Эффект большой: отряд Антуан/Беовульф/Эбигейл + Argon 5 на фикстуре — win rate меняется больше чем на 2 п.п. на 29 из 138 квестов (Sun God's Tomb · босс · Extreme: 0,9 % против 76,8 % при умножении). Переключатель — `PCT_STACKING` в `constants.ts` (`'pooled' | 'multiplicative'`), вариант калибровки `pct-multiplicative` (A57): по отметкам «проходит / не проходит» видно, какое чтение ближе к игре.

Не меняется: «power bonus» второй попытки (A44) и угроза→ATK у Chieftain (A35) остаются отдельными множителями; плоские прибавки боя (DEF щита у Velite A45, дренаж Hemma A46) входят в сумму до %.

## A63 — «Сильная версия» линейки навыка в бою не отличается от слабой · ✅ решено: шаг убран (сессии 22–23)
`skillContributions` меряет вклад «сильной версии» подменой id навыка в слоте (A60), но `stats.ts → activeSkills` выбирает ступень линейки **по стихии героя**, а не по записанному id (`skillTierFor(line, element)`). Поэтому подмена на ступень той же линейки (`strongerInLine`) в бою ничего не меняет: на всех 18 героях фикстуры 52 из 52 подмен дают тот же набор активных навыков, `stronger.contribution === contribution`, и шаг `unblock` плана ролла для реальных героев не появляется (тесты A60 проверяют его на синтетических вкладах). Чтобы «слабая/сильная версия» имела смысл, нужна пара из **разных** линеек с одной иконкой (обычная и эпическая версии навыка) — в данных такой связи нет. Решение за владельцем.

**Сессия 23 — попытка связать пары по иконке (A20).** Гипотеза: одинаковая иконка + разная редкость = слабая/сильная версия. Проверка на фикстуре и дереве fankit stcentral-hub (`public/fankit/Skills/Hero`, 83 файла):
- из 78 Hero-линеек иконка найдена у 52, и **ни одна иконка не общая** для двух линеек — пар среди них нет;
- 26 линеек без иконки — как раз вероятные пары (Sturdy / Toughness / Impervious, Acrobatics / Blurred Movement, Maintenance / Extended Warranty, Fast Learner / Super Genius, Eagle Eyes / Deadly Criticals / Death Dealer…), но у них в fankit **разные** файлы (`s_hp` / `s_megahp`, `s_evasion` / `s_megaevasion`, `s_crit` / `s_megacrit`, `s_break` / `s_superbreak` / `s_megabreak`, `s_xp` / `s_megaxp`), и какая линейка какому файлу соответствует, по имени не определить.

Вывод: связь «одна иконка + разная редкость» по данным **не находится надёжно**. Шаг `unblock` удалён из `rollPlan`, вместе с ним — измерение вклада «сильной версии» в `skillContributions` (оно было холостым и стоило лишних симуляций). Правило гайда осталось текстом в памятке «Как роллить» с оговоркой, что пару нужно проверить по иконке в игре. Вернуть шаг можно, если в таблице или imageMap появится явная связь пар.

## A64 — Погибшие герои в отметках и «Что отметить» · ⚠️ (сессия 24)
После боя игра показывает только исход и **кто погиб**. Оба сигнала теперь идут в калибровку:
- **Отметка** хранит `deadHeroes` (формат отметок v3; имена — как в подписи отряда). У отметок v1/v2 поля нет — «неизвестно»: такие отметки в Brier смертей не входят (`[]` — «никто не погиб» — входят). Старые отметки можно дозаполнить в списке на «Подборе».
- **Симуляция** отдаёт долю боёв, где боец погиб (`SimMetrics.survival[].deathRate`: мёртв в конце боя; при второй попытке Chronomancer — во второй). Это то же, что видно в игре, без HP и раундов.
- **Калибровка**: `CalibrationSummary.deathBrier` = mean((доля смертей − погиб)²) по каждой паре «боец ↔ отметка», `deathAgreement` — при пороге 50 %. Цель подгонки — `brier + CALIBRATION_DEATH_BRIER_WEIGHT × deathBrier` (вес 1 — **допущение**: обе величины Brier одной шкалы, но пар «боец ↔ отметка» в 1–4 раза больше, чем отметок, и смерти внутри одного боя зависимы). В анализе чувствительности — `deathBrierDelta`, он же входит во влияние варианта.
- **«Что отметить»** (`calibration.ts → questsToCheck`, блок на «Данных»): для выбранного отряда (по умолчанию — из последней отметки) каждый квест прогоняется базовой моделью и каждым вариантом `MODEL_VARIANTS` на **общем seed**; квесты ранжируются по разбросу win rate (max − min), подпись — вариант, дальше всех ушедший от базовой модели. Допущения: `CHECK_SUGGEST_RUNS = 200` (по времени: ~6 с на 138 квестов × 21 модель), `CHECK_SUGGEST_MIN_SPREAD = 5 п.п.` («на глаз»: 100 % против 99 % одной отметкой не различить), экипировка — как надета сейчас, а не результат подбора. Разброс — не «информативность» в строгом смысле (ожидаемое уменьшение неопределённости зависело бы от априорных весов вариантов, их нет).

## A66 — Тир предмета героя ограничен его уровнем — и в редакторе, и в подборе · ✅ (сессия 26)

`Max Item Tier` из листа HERO LEVELS — правило игры: выше этого тира герой предмет не наденет
(«носит до T{N}» в форме героя). До сессии 26 редактор его знал, а подбор — нет: оптимизатор брал
только «макс. надетый у героя + 1» (A41), и герою с надетым T4 мог предложить T5, который тот не наденет.

Реализация — одна функция на оба места, `formulas.ts → maxItemTierFor`:
- `constraints.ts → defaultConstraints` — потолок героя = `min(макс. надетый + DEFAULT_ITEM_TIER_HEADROOM,
  Max Item Tier уровня, максимальный тир таблицы)`; без надетых предметов потолок задаёт уровень;
- `optimizer.ts → tierCapFor(data, cons, hi, level)` — при переборе предметов итог = `min(ограничение
  подбора, потолок уровня)`. Это значит, что **переопределение пользователя «Max тир» и сценарий «+1 тир»
  не поднимают тир выше уровня** (A41), а `upgradeScenarios` не предлагает «+1 тир», если уровень не даёт
  ступени выше.
- **Проверка**: `optimizer.test.ts` — «не предлагает предмет выше Max Item Tier уровня героя» (голый герой
  10 ур. с щедрыми ограничениями: все подобранные предметы ≤ T4, и потолок ограничений по умолчанию равен
  ему же) и `tierCapFor` (свой потолок 16 на 1 ур. → T1, на 50 ур. → T16); `constraints.test.ts` —
  «макс. надетый + 1» не выходит за уровень, без надетых потолок задаёт уровень; e2e (уровень и тир) не менялся.
- Что осталось на совести данных: тир камней/духов уровнем не ограничивается — в листах связи «уровень героя →
  тир зачарования» нет, а HERO LEVELS говорит только о предметах (`Max Item Tier` у BLUEPRINTS.Type = Enchantment).

## A67 — Команда: размер отряда, один чемпион и его экипировка (аура + фамильяр) · ✅ / ⚠️ (сессия 27)

Страница «Команды» (сохранённый состав под локацию) держится на трёх правилах.

**1. Размер отряда — `Maximum Party Size` локации · ✅ данные.** Лист QUESTS, заголовок блока каждой локации:
Howling Woods…Cinderlake Volcano — 3, Sun God's Tomb…Meteor Zone — 4, Lost City of Gold — 5
(`src/data/parse/quests.ts → QuestArea.partySize`, `teams.ts → areaPartySize`). Чемпион занимает место в отряде
наравне с героем: 3 героя + чемпион влезают только в локацию на 4. **Нижней границы нет** — по ST-Central
(https://st-central.net/, раздел про отряды) типовой состав «1 чемпион + 3 героя», но игра допускает и 4 героев
без чемпиона, и соло с дуэтом; поэтому проверка (`teams.ts → validateParty`) сообщает только о превышении
размера и о пустой команде. **«Не больше одного чемпиона»** — правило игры, в модели это `Team.champion`
(один) плюс `extraChampions` для чужих/старых записей: их наличие — ошибка состава, а не молчаливая потеря.

**2. Что носит чемпион · ⚠️ допущение.** У чемпиона нет слотов класса: ни в HEROES (там только 21+21 класс),
ни в CHAMPIONS (там ранги, монеты и лидерские навыки). В BLUEPRINTS есть два типа предметов поддержки,
не встречающихся ни в одном слоте классов (SCHEMA.md → «Dual Wield, Familiar, Aurasong не встречаются ни в одном
слоте классов»): **Aurasong** (21 предмет, T3–T16, статы — DEF и немного HP/ATK) и **Familiar** (18 предметов,
ATK/DEF/HP/EVA/CRIT). Моделируем: чемпион = база + награды рангов + статы аурасонга и фамильяра (с множителем
качества, A7) + навык аурасонга + навык духа, вставленного в фамильяр.

- **Связь аурасонга с навыком — по имени предмета**: у этих 21 предмета BLUEPRINTS поле `Spirit Affinity` пусто,
  а в SKILLS есть ровно 22 строки `Type = Aurasong` (21 аура + `Alien Aura`), и `Name` совпадает с именем предмета
  (`Aura of Inspiration` — и предмет, и навык). Другой связи в данных нет (у предметов нет колонки «навык», как
  у артефактов). Реализация: `combat.ts → championEquipment`.
- **Эффекты аур парсер уже понимает**: `Grants +12% bonus Attack and Defense, as well as +12% HP to the party` →
  три эффекта `scope = 'party'` (`skillEffects.ts`), и в бою их получает **весь отряд**, включая самого чемпиона
  (`combat.ts → prepare` раскладывает party-эффекты по всем бойцам). Проверено тестом: у героя без ауры и с аурой
  различаются `selfStatic` и `maxHp`.
- **Гайд Develion** (ссылка в A9) называет «Ауру Вдохновения» сбалансированным выбором, рекомендует фамильяра
  с наибольшими защитой/здоровьем, а из духов — Тараска (в таблице — **Tarrasque Spirit**, `+20% Defense`) для
  выживаемости защитника; «дух Исполина» — если не хватает силы героя. Духи в данных: `Titan Solemnity`
  (`+15% Health, +15% Mana Shield`), `Behemoth Violence` (`+13% Attack, +5% Defense`), `Hydra Onslaught`
  (`+100 Defense, +25 Health`). Отдельного правила «дух Исполина» в таблице нет: выбор духа остаётся за
  пользователем, движок считает любой выбранный.
- **Качество ауры не меняет силу ауры**: `Aura of Inspiration` Normal и Legendary дают один и тот же навык
  (проверено тестом), меняются только DEF/HP самого предмета — это ровно то, что говорит гайд.
- **Правило сродства духа то же, что у героя** (A5): «+»-версия включается, если `Spirit Affinity` фамильяра
  совпадает с навыком духа. Правило «дух вставляется в любой предмет» (A65) сюда тоже переносится: список духов
  в форме полный.
- **Что не проверено:** носит ли чемпион ещё что-то (в таблице таких полей нет) и совпадают ли статы аурасонга
  на экране игры (предмет «носит» чемпион, а не герой). Что закроет вопрос: экран чемпиона в игре.

**3. Прогон и отметки.** Win rate, гибель каждого бойца (`SimMetrics.survival[].deathRate`), средние раунды,
барьер (`barrierSummary`) и доли одиночных ударов босса (`attackShares` = `(1 − p_AoE) × threat / Σ threat`,
как в бою) — `src/engine/teamRunner.ts`. Прогон **детерминирован** (`TEAM_SIM_SEED`, seed + номер квеста),
команды сравниваются на одном seed — как CRN в оптимизаторе (A38). Отметка «прошёл / погибли» с «Команд»
пишется в тот же журнал, что и с «Подбора» (`realityChecks.ts`), и отличается только `teamLabel` (имена команды).

**4. Хранение.** Команда хранит **снимок** героев (экипировка, навыки, уровень, Душа) и ссылку `heroId`:
команда должна оставаться воспроизводимой, даже если героя потом переоденут, а ссылка нужна для «обновить из
героев». Кнопка «Подобрать экипировку» передаёт состав и чемпиона в оптимизатор через строку запроса
(`optimize.tsx → validateSearch`), и подбор считает **того же** чемпиона (`OptimizerInput.championBuild`), иначе
win rate подбора разошёлся бы с прогоном команды (проверено тестом: win rate подбора = прямой прогон).

## A69 — План команд: жадный сбор, обмены и цели улучшения · ⚠️ эвристика (сессия 28)

**Что из данных.** Число отрядов ограничено размером локации (`Maximum Party Size`, A67) и размерами ростера:
n отрядов требуют n×P мест, чемпион занимает место героя; чемпионов на отряды не больше, чем доступных (каждый
чемпион — в одной команде, правило 2). Порядок чемпионов: сначала «добытчики» Sia/Polonia/Malady
(`LOOT_CHAMPIONS`), затем тот, у кого есть бонус стихии против барьера (Rudo, A68), затем чемпионы-бойцы
(`FIGHTER_CHAMPIONS`) — так требует владелец и так устроены их лидерские навыки.

**⚠️ Эвристика, подобранная без игровых данных** (в источниках планировщика нет):
- **Жадный сбор**: на отряд сначала набирается стихия барьера (не меньше двух вкладчиков — правило 1), затем
  «красный» (правило 3), затем свободные слоты — синие/зелёные по `quickScore` (правило 4). «Сначала самое
  трудное» = сначала барьер и добыча, как просил владелец.
- **Улучшение обменами**: кандидаты — обмены «сильный герой в слабую команду» и «вкладчик стихии туда, где барьер
  не пробит»; отбор кандидатов — по `quickScore` и вкладу в стихию (быстрая оценка), **решение — симуляция**
  (тот же приём, что в оптимизаторе экипировки, A38). Обмен, оставляющий отряд без «красного», не рассматривается.
- **`PLAN_SIM_RUNS = 300`** на команду в фазе улучшения и **`PLAN_FINAL_RUNS = 1000`** в итоговом отчёте;
  **`PLAN_SIM_BUDGET = 300`** вызовов симуляции, **`PLAN_SWAP_CANDIDATES = 12`** кандидатов за проход,
  **`PLAN_IMPROVE_PASSES = 5`** проходов — числа выбраны по времени расчёта (как `CHECK_SUGGEST_RUNS`, A64).
- **Цель улучшения**: «сумма win rate» или «число команд с win rate ≥ порога» (`PLAN_WIN_THRESHOLD = 0.5`);
  при цели по порогу равенство по числу команд разрешается средним win rate. Формулировка цели — требование
  владельца, конкретный тай-брейк — наш выбор.
- **Экипировка чемпиона в плане пустая** (аура/фамильяр/дух): план подбирает состав и чемпиона, а экипировка
  задаётся на странице «Команды» (A67). Из-за этого win rate плана может быть ниже, чем у сохранённой команды с
  аурой, — в интерфейсе плана это сказано.
- **Стартовая оценка не отменяется**: `cancel()` останавливает фазу обменов и итоговый пересчёт, но первая
  оценка (по одной симуляции на отряд) выполняется всегда — иначе плану нечего показать. В интерфейсе есть
  прогресс и кнопка «Отменить»; расчёт идёт в Web Worker (`engine.worker.ts → planTeams`).
