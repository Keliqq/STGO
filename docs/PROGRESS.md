# Прогресс

## Сессия 28 — 2026-10-12: правила ST-Central в редакторе команды, план команд на локацию, барьеры и анализ ростера

Требования владельца: (1) подсказки в редакторе команды — правила 1–4 (галочка/предупреждение) и пары
«чемпион ↔ герой» по признакам героя (EVA после штрафа, крит без защитных навыков, угроза, класс), каждая
подсказка с источником, а рядом — кнопка «проверить симуляцией» (прогон с предложенным чемпионом и с
текущим); (2) «План команд на локацию»: локация + сложность → максимум команд из ростера (каждый
герой/чемпион — в одной команде), жадно по правилам 1–4 (сначала трудные барьеры и чемпионы с добычей
Sia/Polonia/Malady), затем улучшение обменами героев по симуляции (цель — сумма win rate или число команд
с win rate ≥ порога), время — в Worker с прогрессом и отменой; (3) «Барьеры»: таблица локация × сложность
(QUESTS: Barrier Type/Health), вклад героев и чемпионов (Spellblade 50%, Rudo +50%, чемпион по рангу),
готовые барьерные пары (2 героя / герой + чемпион / герой + Spellblade) и чего не хватает; (4) «Анализ
ростера»: героев и архетипов на стихию, бойцы против слотов квестов, синие против зелёных, что нанять;
(5) константы правил в `constants.ts` с источником, тесты, PROGRESS, коммит, push.

Источники правил (у каждой подсказки в интерфейсе — ссылка): ST-Central «Team Building, Not Guesswork»
(https://st-central.net/team-building-not-guesswork/), «Foster Your Roster»
(https://st-central.net/foster-your-roster/) и «Гайд по героям и защитникам Shop Titans 2.0» (Develion,
https://docs.google.com/document/d/1DrP0VBxnDPSLwsLe_Y8T3BkrGmN_f6QiBGrHW1qs3E8). Разбор — A68, A69.

### Правила и пары «чемпион ↔ герой» (`src/engine/teamRules.ts`)
- **Правила 1–4** проверяются по фактам бойцов (`partyFacts`: класс и группа, стихия и вклад в стихии барьера,
  уклонение после штрафа Extreme, крит, доля ударов по угрозе, DEF, число защитных навыков):
  два героя на стихию барьера, один чемпион, один «красный» (Fighter), остальные слоты — «синие/зелёные».
  `warn` — только нарушение правила; всё остальное — `info`/`ok`, то есть «подсказка не приговор».
- **Пары «чемпион ↔ герой»**: уклонение после штрафа (≥95% → Lilu, 85–95% → Donovan/Malady/Polonia,
  75–85% → Yami), крит ≥40% без защитных навыков → Rudo/Bjorn, угроза (доля ударов ≥50%, а DEF ниже порога
  70% квеста → предупреждение), класс (связки Develion: Donovan ↔ разбойники, Lilu ↔ Wanderer/Pathfinder,
  Polonia ↔ Trickster/Thief), сильные герои → Sia, слабые → Argon, боссовый квест → Ashley, барьер не пробит →
  чемпион с «+50% party Element bonus» (Rudo), Malady/Reinhold → нужен боец с высокой угрозой.
- **«+50% стихии отряда» у Rudo — награда 7-го ранга** («Berserker Rampage»): «R7» из статьи подтвердился
  данными (тест в `barriers.test.ts`), константа `BARRIER_BONUS_SKILL_RE`.
- **Связка «Gemma + 3 Chieftain»** не кодируется: чемпиона Gemma в листе CHAMPIONS нет (13 чемпионов) — записано
  в A68, а не выдумано.
- **Интерфейс** (`teams.tsx → PartyHintsView`): блок «Подсказки по составу (ST-Central)» в редакторе команды —
  бейдж уровня, текст, ссылка «источник» и кнопки «проверить симуляцией: <чемпион>». Кнопка прогоняет тот же
  состав с текущим и с предложенным чемпионом на выбранном квесте (тот же ранг и та же экипировка чемпиона) и
  показывает «без чемпиона: 45.0% → Argon (ранг 1): 61.2%». Проверка идёт через воркер, как прогон команды.

### «Барьеры» (`src/engine/barriers.ts`)
- Строка на каждый квест с барьером (43 из 138): стихии и `Barrier Health` из QUESTS, размер отряда локации.
- **Вкладчики**: герой — своей стихией (A21, с духами A29), Spellblade/Spellknight — `elementAny × 50%` в любую
  стихию (A9), чемпион — стихией по рангу (Element Breakpoints, A13). Бонус Rudo (+50%) показывается отдельно и
  как множитель к сумме отряда.
- **Готовые пары** (`heroes` / `hero+champion` / `hero+spellblade` / `spellblades`) с порогом: пара из отчёта
  проверяется боевой логикой (`combat.ts → barrierBroken`) — тест «барьерные пары достигают порога». Пара из двух
  чемпионов не предлагается (в отряд встаёт один чемпион, правило 2).
- **Сколько таких отрядов можно собрать** — максимум непересекающихся пар (`maxDisjointPairs`), отдельно с
  бонусом Rudo.
- **Чего не хватает**: сколько стихии недостаёт лучшей паре, сколько камней какого размера добрать (самый
  крупный камень стихии из ENCHANTMENTS), поможет ли Rudo, хватает ли отряда целиком и есть ли в ростере
  вкладчики этой стихии вообще.
- **Интерфейс**: таблица с фильтром по локации (локация, сложность, тип, стихии, нужно, лучшая пара, сколько пар
  хватает) и «Разобрать» — вкладчики, пары и советы по строке; кнопка «Построить план на этот квест» переводит в
  план. Ранги чемпионов правятся в сворачиваемом блоке (по умолчанию — из сохранённых команд, ранг 0 = «нет»).

### «План команд на локацию» (`src/engine/teamPlan.ts`, воркер)
- **Сколько команд влезает**: n отрядов требуют n × (размер локации) мест, чемпион занимает место героя,
  каждый чемпион — не больше чем в одну команду.
- **Жадный сбор**: чемпионы по приоритету (Sia/Polonia/Malady → Rudo при непробитом барьере → чемпионы-бойцы),
  затем на отряд — стихия барьера (не меньше двух вкладчиков), «красный», остальное — «синие/зелёные» по
  `quickScore`. Шаги сбора сохраняются в `notes` отряда — план объясним.
- **Улучшение обменами**: кандидаты «сильный герой в слабую команду» и «вкладчик стихии туда, где барьер не
  пробит» отбираются по `quickScore` (A38: быстрая оценка только отбирает), решение принимает симуляция; обмен,
  оставляющий отряд без «красного», не рассматривается. Цель — сумма win rate или число команд с win rate ≥
  порога (`PLAN_WIN_THRESHOLD`), при равенстве по числу команд сравнивается средний win rate.
- **Прогресс и отмена**: `planTeams` — чистая функция с `onProgress`/`shouldCancel`; в приложении считается в
  воркере (`Engine.planTeams`), в интерфейсе — полоса прогресса «симуляций X из Y» и кнопка «Отменить».
  Стартовая оценка (по симуляции на отряд) не отменяется — иначе плану нечего показать (A69).
- **Сохранение**: «Сохранить в „Команды“» создаёт по команде на отряд (снимки героев, чемпион, целевая
  локация) — экипировка чемпиона задаётся там же (план её не подбирает, A69).
- Каждый отряд получает те же подсказки по правилам, что и редактор команды, и строку барьера (сколько даёт,
  пробит ли).

### «Анализ ростера» (`src/engine/roster.ts`)
- Таблица по шести стихиям и «Any»: героев, из них реально дающих стихию (с камнями), архетипы (Fighter/Rogue/
  Spellcaster) и чего не хватает до «3+ героя, 2+ архетипа». Spellblade («Any») за стихию не считается —
  это правило «Foster Your Roster».
- Бойцы (Fighter) против слотов квестов: слоты берутся из листа SLOTS (максимум 15), по умолчанию — сколько
  отрядов набирается из ростера; поле в интерфейсе переопределяет. Синие (Spellcaster) сравниваются с зелёными
  (Rogue) с допуском 1.
- «Что нанять следующим» — список советов с источником: героев на стихию, второй архетип (или оговорка, что
  его в игре нет), бойцы под слоты, перекос синих/зелёных.

### Дальше / известные проблемы
- **Границы советов по уклонению** (0,75/0,85/0,95) и порог угрозы 50% — трактовка слов статьи (A68): если
  найдётся точная формулировка ST-Central, полосы стоит поправить.
- **«Gemma + 3 Chieftain»** из гайда Develion закодировать нельзя: этого чемпиона нет в листе CHAMPIONS.
- **Ранги чемпионов вводятся вручную** (по умолчанию из сохранённых команд): в приложении нет справочника
  «какие чемпионы открыты у пользователя». Ранг 0 = «нет чемпиона» — это соглашение интерфейса, не игры.
- **План не подбирает экипировку чемпиона** (аура/фамильяр): win rate плана ниже, чем у сохранённой команды с
  аурой. Возможное развитие — переносить ауру из существующей команды того же чемпиона.
- **Обмены — локальный поиск**: кандидаты отбираются по `quickScore` и вкладу в стихию (A69), при большом
  ростере (10+ отрядов) бюджет `PLAN_SIM_BUDGET` может не покрыть все пары — план останется «жадным с
  улучшением», а не оптимальным.
- **Slots квестов** по умолчанию выводятся из размера ростера, а не из аккаунта (в данных есть только максимум
  15 из SLOTS) — поле в интерфейсе исправляет это вручную.

## Сессия 27 — 2026-10-12: страница «Команды» — сохранённые отряды, экипировка чемпиона, прогон и сравнение

Требования владельца: (1) страница «Команды» — сохранённые команды (имя, герои, чемпион + ранг + аура +
фамильяр + духи, целевая локация/сложность) с проверкой состава под локацию (размер, один чемпион);
(2) если ауры и фамильяры чемпиона в движке не моделируются — смоделировать по листам SKILLS (`Aurasong`)
и BLUEPRINTS, допущения — в ASSUMPTIONS; (3) прогон команды: win rate по выбранным квестам, вероятность
гибели каждого героя и чемпиона, средние раунды, барьер (кто сколько стихии вносит) и доля ударов босса
по каждому; сравнение 2–3 команд бок о бок на одном квесте; (4) «Подобрать экипировку для этой команды» —
существующий оптимизатор с составом команды; (5) отметка «прошёл/погибли» из «Данных» привязывается к
команде; (6) тесты (валидация размера/чемпиона, детерминизм прогона с seed), e2e, PROGRESS, коммит, push.

### Экипировка чемпиона — смоделирована (A67)
- **В движке её не было**: `fighterFromChampion` знал только базу, награды рангов, стихию по Element
  Breakpoints и лидерский навык. Добавлен `ChampionBuild` (`combat.ts`): чемпион, ранг, аурасонг (предмет +
  качество), фамильяр (предмет + качество) и дух в фамильяре. `fighterFromChampion(champion, rank, data, build)`
  прибавляет статы предметов с множителем качества и навыки: аурасонга — с `Type = Aurasong` и **тем же именем**,
  что у предмета (другой связи в листах нет: у аурасонгов `Spirit Affinity` пусто), духа — по правилам сродства
  A5 («+»-версия при совпадении `Spirit Affinity` фамильяра с навыком духа).
- **Эффекты аур уже разбирались парсером** как `scope = 'party'` — в бою их получает весь отряд (`prepare`),
  включая чемпиона. Тест: «бонус ауры получают все бойцы отряда, а не только чемпион».
- **«Аура Вдохновения»** (`Grants +12% bonus Attack and Defense, as well as +12% HP to the party`) —
  сбалансированный выбор из гайда Develion; **качество ауры силу ауры не меняет** — только DEF/HP предмета
  (проверено тестом). Ненайденный предмет/дух не выдумывается: попадает в `championEquipment(...).notes`,
  UI показывает предупреждение, оптимизатор — в `warnings`.
- **Оптимизатор**: `OptimizerInput.championBuild` (необязательное поле). Есть — подбор считает того же
  чемпиона, что и прогон команды; нет — прежнее поведение (голый чемпион), обратная совместимость.
  Тест: win rate подбора совпадает с прямым `simulateTeam` на том же наборе.

### «Команды» (`src/routes/teams.tsx`, `src/data/teams.ts`, `src/engine/teamRunner.ts`)
- **Модель и хранение** (`teams.ts`): `Team` = имя, участники (снимок героя + ссылка `heroId`), чемпион с
  экипировкой, целевая локация (id квеста), заметка, времена. Снимок — чтобы команда оставалась
  воспроизводимой после переодевания героя; ссылка — для «Обновить из героев» (`fitMemberToHero`).
  IndexedDB-ключ `teams`, версия записи 1; команды попали в резервную копию (`appState.ts` → версия 3,
  старые файлы 1–2 читаются: команд в них просто нет).
- **Проверка состава** (`validateParty`): размер отряда = `Maximum Party Size` локации (3/4/5, чемпион
  занимает место), «не больше одного чемпиона» (`extraChampions` — для чужих/старых записей), пустая команда.
  Нижней границы нет: соло и дуэт разрешены (ST-Central: типовой состав 1 чемпион + 3 героя, но игра
  допускает и 4 героев без чемпиона). Герой может быть в нескольких командах-вариантах — на карточке видно,
  в каких ещё командах он есть.
- **Прогон** (`teamRunner.ts`): на квест — `simulateTeam` в воркере (`Engine.runTeam`, `engine.worker.ts`),
  `TEAM_SIM_RUNS = 2000` как у оптимизатора, seed — `TEAM_SIM_SEED` + номер квеста (детерминизм: тест
  «один и тот же seed даёт одинаковые метрики»). Метрики: win rate и средние раунды, доля гибели и выживания
  каждого бойца, вклад в стихии барьера, доли **одиночных** ударов босса (`(1 − p_AoE) × threat / Σ threat` —
  как в бою), «пробит ли барьер» с бонусом отряда к стихии (Rudo).
- **Интерфейс**: список команд (состав, размер, проверка, отметка), редактор (герои, чемпион с рангом, аурой,
  фамильяром и духом, целевая локация, «Обновить из героев»), «Прогон и сравнение» — 2–3 команды на одном
  квесте в двух таблицах (итоги и участники) и отметка «прошёл / погибли» по каждой команде.
  Кнопка «Подобрать экипировку» уводит в «Подбор» ссылкой (`validateSearch`): состав, чемпион, его экипировка
  и целевой квест подставляются в форму.
- **«Подбор» заодно**: до 5 героев вместо трёх (правило владельца), поля ауры/фамильяра/духа чемпиона в форме
  отряда, `aria-label` у полей чемпиона (иначе «Чемпион» и «Аура чемпиона» не различить по подписи).

## Сессия 18 — 2026-10-12: шаг unblock только под реальную цель 4-го слота и одно действие на слот в плане ролла

### Задача
Владелец уточнил правило вывода шага-разблокировки в `skills.ts → rollPlan`: шаг `unblock` показывать, только если
сильная версия этой линейки **входит в цель для 4-го слота** — её вклад больше вклада текущей слабой версии и она есть
в `rollableSkills` после снятия блокировки. Иначе шага нет, и оговорка «можно пропустить» в тексте шага не нужна.
Плюс: в одном плане не должно быть одновременно «оставить» и «сроллить» для одного слота. Тесты на оба случая,
PROGRESS, коммит, push.

### Что сделано
- **Вклад сильной версии теперь измеряется** (`skills.ts → skillContributions`): для каждого навыка с вкладом выше
  `eps` (то есть того, который совет оставляет) считается его «парная» сильная версия — симуляцией того же отряда с
  подменой навыка в том же слоте. База сравнения — та же пустая слот-позиция (`wrWithout`), поэтому вклады слабой и
  сильной версий сравнимы напрямую: `contribution(strong) − contribution(weak) = win rate с сильной − win rate со
  слабой`. Сильная версия попадает в `SkillContribution.stronger` / `SkillAdvice.stronger` (`{ skillId, skillName,
  contribution }`) и доезжает до плана через воркер; `rollPlan` по-прежнему без симуляций.
- **Шаг `unblock` — только под реальную цель 4-го слота**: недостаточно, чтобы у слабой версии была ступень выше.
  Нужно, чтобы (1) сильная версия была сильнее по вкладу (`stronger.contribution > contribution` слабой) и (2) она
  попадала в `rollableSkills` после снятия блокировки (`ignoreSlots: [слот слабой версии]`) — то есть была доступна
  классу/промоушену и не блокировалась правилами оружия. Иначе шага нет — слабую версию не трогаем. Оговорка «если
  сильная версия этой линейки не нужна — шаг можно пропустить» удалена: в шаге теперь видны оба вклада и разница, а
  если цель не подтверждается данными, шага просто нет.
- **Следствие, важное для интерфейса:** у героя базового класса без Души Титана сильные T4-версии линеек помечены
  `Requires Class Promotion`, в пул не попадают — шаг не выводится. Шаг появляется у героя промоушена (или с Душой
  Титана), поэтому в тестах план проверяется на герое класса промоушена (`pairClass` линейки), а скриншоты e2e
  (в фикстуре все 18 героев — базовые классы) новый шаг не показывают.
- **Один слот — одно действие** (`HeroSkillPlan.slotActions`): итог плана по каждому слоту, где шаг плана («сроллить»:
  найм, кубик, разблокировка, Роланд) важнее вердикта совета («оставить»). Карточка героя (`SkillAdviceView`) теперь
  берёт вердикт из `slotActions`: если совет советует оставить навык, а план его перекидывает шагом-разблокировкой,
  показывается «перекинуть по плану», а не «оставить»; найм и Роланд подписаны «перекинуть наймом / Роландом».
  Одновременно «оставить» и «сроллить» для одного слота в плане не выводится.
- **Несколько целей 4-го слота:** сильных версий может быть несколько (по одной на снятую блокировку) — тогда в шаге
  перечисляются все доступные цели, а ожидаемое число бросков считается как пул / число целей (вероятность выпадения
  любой из них), например 2 цели при пуле 100 → ≈ 50 бросков. Раньше в цель бралась первая попавшаяся пара, и оценка
  была завышена вдвое.
- **Документы:** A60 — новое условие шага и следствие про промоушен, инвариант «один слот — одно действие», оценка
  бросков при нескольких целях.

## Сессия 13 — 2026-10-10: объяснения «почему», веса статов, ограничения на героя, семена

### Задача
Пользователь должен понимать, ПОЧЕМУ программа выбрала именно эти вещи: какой стат дал каждый
предмет и сколько это в win rate/уроне, что вообще важно герою на этом квесте, кто принимает
удары, чего не хватает для барьера. Плюс — ограничения на героя (а не на отряд) и совет по семенам.

### Что сделано
- **Веса статов** (`src/engine/statWeights.ts`, A55/A56): для каждого героя отряда симуляцией на
  подобранном наборе измеряется прирост от `+1% CRIT`, `+10% CRIT DMG`, `+1% EVA`, `+5% ATK/HP/DEF`,
  `+10 стихии`, `+10 угрозы`. Все варианты (и база) считаются на общем seed — CRN, поэтому разница
  не шум. Метрика выбирается по win rate квеста: не насыщен → п.п. win rate; 100% → урон за раунд
  (для HP/DEF/EVA — мин. % HP выжившего, добавка защиты урон не увеличивает).
- **Ослабленный зонд** (A56): если win rate 0% (отряд проваливается всегда, любая прибавка стата
  «не меняет» исход), веса считаются на том же квесте с ослабленными HP (÷ factor) и уроном монстра
  (÷ √factor) — из перебора факторов берётся тот, у которого win rate ближе к 50%; победитель
  пересчитывается на полном числе прогонов. UI помечает такие веса.
- **Добавка статов в бою** (`combat.ts → FighterBonus` / `applyFighterBonus`): поля ATK/DEF/HP,
  крит, крит-урон, уклонение, угроза и стихия; применяются в `prepare` и `runAttempt` и в
  `quickScore`, поэтому веса и оптимизатор видят одно и то же.
- **UI**: в «Результате» — блок «Почему именно эти статы: веса статов» (одна фраза «Главное для
  героя: …» на каждого героя + столбики по отряду + таблица «Прибавка / Win rate / Урон / Мин. HP»);

- **Угроза в группе**: доли атак босса по каждому бойцу (`combat.ts → threatShares`: 20% AoE по всем,
  остальное — по `threat / Σ threat`) показываются столбиками; если ДД получает больше танка

- **Барьер**: `combat.ts → elementContributions` + `statWeights.ts → barrierInfo` — стихия группы

- **Ограничения на героя** (A41 обновлено): «макс. тир = макс. надетый у ЭТОГО героя + 1»

  верхней границей для переопределений пользователя; ручной список духов снимает per-hero тиры.

- **Совет по семенам** (A55): какое одно семя (ATK/HP/DEF) даёт больше на героя — из весов (шаг =

## Чего не хватает в таблице

Критично для движка:
1. **Множители качества** (Normal/Superior/Flawless/Epic/Legendary) для статов предметов, а также для камней и духов (A7).
2. **Прирост статов героя по уровням.** HERO LEVELS содержит только XP и максимальный тир, HEROES — одно значение на класс (A8).
3. **Пороги защиты квестов** (DEF → 50/70/75% снижения урона) — только на stcentral-hub, лицензия ND (A10). Для Lost City of Gold нет нигде. *Сессия 2: загружаются в рантайме.*
4. **Формулы боя:** урон героя по монстру, снижение урона от DEF между порогами, вероятность и частота AoE, выбор цели по Threat, работа EVA/CRIT/Mana Shield, лимит раундов, условие провала.
5. **Механика стихийного барьера:** порог или пропорция, как суммируется стихия отряда, вклад чемпиона и стихии героя, «Any» у Spellblade (A9).
6. **Эффект Elemental Affinity** и условие навыка духа «+» (A5, A6).
7. **Как статы зачарования складываются со статами предмета** (полностью ли, масштабируются ли качеством камня или предмета).
8. Боевые апгрейды предмета — Starforged (`+25% Base ATK, DEF and HP`, `DEF +20`) и Transcendence (`ATK +2`, `+10% Base …`). Данные есть, но нужно знать, какие апгрейды у конкретного предмета пользователя → это поля инвентаря, а не таблицы.

Менее критично:
9. Типы `Dual Wield`, `Familiar`, `Aurasong` не встречаются ни в одном слоте классов. Возможно, это экипировка чемпионов или особые правила.
10. `Built-In Spirit = Mundra's Spirit` — такого духа нет в ENCHANTMENTS и SKILLS.
11. Чемпионы `Aang`, `Sokka` есть в SKILLS (`Classes`), но отсутствуют в CHAMPIONS.
12. Нет заголовков у колонок-иконок (ресурсы в BLUEPRINTS, стихии в ENCHANTMENTS, колонка 4 в SKILLS) — восстановлены выводом (A2, A3, A12).
13. Нет ID линеек навыков. Линейка определяется по соседним строкам и росту Tier.
14. Нет идентификаторов для картинок (slug для playshoptitans.com / stcentral-hub fankit) — *решено в сессии 2: `imageMap.json`, см. SCHEMA → «Внешние id».*
15. Названия боссов и саб-локаций — только на stcentral-hub.
